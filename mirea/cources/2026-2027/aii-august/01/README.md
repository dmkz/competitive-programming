# Бинарный поиск по ответу

## 1. Углубляемся в бинарный поиск

В прошлом интенсиве мы уже пользовались бинарным поиском в отсортированных массивах. Тогда он всегда выглядел как вызов готовой функции: мы сортировали массив и просили библиотеку найти нужную границу.

Это хороший способ решать конкретную задачу, но для **бинарного поиска по ответу** готовой функции уже не будет. Придётся самостоятельно выбрать границы, написать проверку и доказать, что поиск не потеряет ответ.

Начнём со знакомой **задачи**. Дан отсортированный массив `a` из $n$ чисел и число $x$. Требуется найти индекс первого элемента, который не меньше $x$. Если такого элемента нет, ответом будет $n$.

## 2. Решение через `lower_bound`

В прошлом интенсиве в C++ мы использовали `lower_bound`. После сортировки массива достаточно было вычесть из полученного итератора его начало:

```cpp
sort(a.begin(), a.end());
int pos = lower_bound(a.begin(), a.end(), x) - a.begin();
```

Значение `pos` находится в пределах от `0` до `n`. Если `pos < n`, то `a[pos] >= x`, а все элементы левее `pos` строго меньше $x$.

> [!NOTE]
> Значение `pos == n` означает, что подходящего элемента в массиве нет. Это нормальный результат `lower_bound`: итератор указывает на позицию сразу за концом массива.

Помимо `lower_bound` были ещё:

- **`upper_bound`** находит первый элемент, строго больший $x$.
- **`equal_range`** возвращает обе границы вхождений $x$.
- **`binary_search`** отвечает только на вопрос, есть ли $x$ в диапазоне.

В Python3 тот же результат давал `bisect_left`:

```python
from bisect import bisect_left

a.sort()
pos = bisect_left(a, x)
```

Здесь `pos` тоже может равняться `len(a)`. Модуль `bisect` *не сортирует* список сам: условие о порядке элементов остаётся нашей ответственностью.

> [!WARNING]
> Ни `lower_bound`, ни `bisect_left` не исправят неотсортированный массив.
>
> Без отсортированного порядка элементов в массиве граница «первого подходящего» не обязана существовать.

## 3. Ручная реализация

Для освоение бинарного поиска по ответу важнее всего научиться писать его вручную. Нужно думать, как бинарный поиск, стать бинарным поиском...

Разберём внутреннюю идею этих готовых функций. Возьмём один вариант реализации и будем использовать его дальше: поиск на полуинтервале $(low, high]$.

> [!TIP]
> Если задача буквально просит первую позицию `>= x` в отсортированном массиве, `lower_bound` или `bisect_left` надёжнее и короче ручной реализации.
>
> Ручной поиск нужен, когда проверка кандидата уже не сводится к сравнению с элементом массива.

Пусть индексы массива идут от $0$ до $n-1$.

> [!NOTE]
> Введём две служебные позиции:
>
> - `low = -1` означает позицию перед массивом.
> - `high = n` означает позицию сразу после массива.

В самом начале левая граница точно не подходит условию «элемент не меньше $x$»: перед массивом нет элемента, который мог бы быть ответом.

Правая граница, наоборот, подходит как служебный ответ: если в массиве нет подходящего элемента, `lower_bound` как раз возвращает $n$.

> [!IMPORTANT]
> <u>В течение поиска `low` всегда обозначает гарантированно неподходящую позицию, а `high` – гарантированно подходящую.</u> Мы не обращаемся ни к `a[-1]`, ни к `a[n]`.

Пока между границами есть хотя бы один индекс, смотрим на середину. Если `a[mid] >= x`, середина подходит и может стать новой правой границей. Иначе она не подходит и становится новой левой границей.

```cpp
int low = -1, high = n;
while (high - low > 1) {
    int mid = (low + high) / 2;
    if (a[mid] >= x) high = mid;
    else low = mid;
}
cout << high << '\n';
```

Python3 отличается только синтаксисом целочисленного деления:

```python
low, high = -1, n
while high - low > 1:
    mid = (low + high) // 2
    if a[mid] >= x: high = mid
    else: low = mid
print(high)
```

> [!IMPORTANT]
> Пока выполнено `high - low > 1`, середина лежит между границами, то есть от `low + 1` до `high - 1`. При наших начальных границах это всегда настоящий индекс от $0$ до $n-1$, поэтому обращение `a[mid]` безопасно.

> [!IMPORTANT]
> Когда цикл завершится, `high = low + 1`. Полуинтервал $(low, high]$ содержит единственное целое значение `high`, которое остаётся подходящим по инварианту. Значит, `high` и есть ответ.

Например, для `a = [1, 3, 3, 7, 10, 14, 20]` и $x=8$ поиск идёт так:

| шаг | `low` | `high` | `mid` | `a[mid] >= x` |
| --- | ---: | ---: | ---: | --- |
| начало | -1 | 7 | – | границы заданы |
| 1 | -1 | 7 | 3 | нет |
| 2 | 3 | 7 | 5 | да |
| 3 | 3 | 5 | 4 | да |

После третьей проверки границы равны `low = 3` и `high = 4`. Дальше идти некуда: `a[3] = 7` ещё меньше $8$, а `a[4] = 10` уже не меньше. Ответ – индекс $4$.

Полная реализация с вводом массива и $x$ находится в [C++](Part-01-Search-Boundary/examples/example-01.cpp) и [Python3](Part-01-Search-Boundary/examples/example-01.py).

<details>
<summary><strong>Пример запуска</strong></summary>

```text
Ввод
7
1 3 3 7 10 14 20
8

Вывод
4
```

</details>

Для поиска по массиву из $n$ элементов требуется $O(\log(n))$ проверок, потому что длина промежутка между границами после каждого шага уменьшается хотя бы примерно вдвое. Дополнительная память не используется.

## 4. Как мы сужаем отрезок и меняем границы

> [!TIP]
> В этой реализации **не нужно запоминать**, где ставить `+1` или `-1`. Нужно только спросить, подходит ли `mid`.
>
> - Если подходит, заменяем им границу, которая отвечает за «подходит».
> - Если не подходит, заменяем им границу, которая отвечает за «не подходит».

> [!IMPORTANT]
> Ответом всегда будет та граница, роль которой соответствует искомой позиции.

В примере мы ищем первый подходящий индекс, поэтому выводим `high`. При таком соглашении не нужно отдельно придумывать поправки к середине: они уже заложены в полуинтервале и в двух ролях границ.

> [!NOTE]
> Почему именно `low = -1` и `high = n`, а не, например, `low = 0` и `high = n + 1`?

Здесь нет универсальной формулы. Для выбранного поиска нужно подобрать две позиции с доказанными ролями: одна точно не подходит, другая точно подходит. В `lower_bound` такие позиции дают сам массив и два естественных служебных индекса. Значение `a[0]` может уже быть не меньше $x$, поэтому оно не годится на роль гарантированно неподходящей левой границы. А `n` уже является естественным ответом в случае, когда в массиве ничего не найдено. Дополнительная позиция `n + 1` здесь не нужна.

> [!TIP]
> Для рассуждений можно вообразить два служебных значения: $a[-1] = -\infty$ и $a[n] = +\infty$.
>
> Это только математическая модель. В программе эти элементы не существуют и никогда не читаются.

## 5. Пространство поиска и предикат

Теперь отделим конкретный массив от общей схемы. **Пространство поиска** – это непрерывный отрезок возможных ответов. Если известно, что ответ лежит в $[L, R]$, то искать нужно именно на этом отрезке.

> [!NOTE]
> В коде мы храним полуинтервал между двумя границами. В рассуждениях обычно удобнее говорить о самом отрезке возможных ответов.

В задаче с `lower_bound` пространство поиска – $[0, n]$. Индексы от $0$ до $n-1$ обозначают настоящие элементы массива, а $n$ – служебную позицию сразу после него. Для настоящего индекса $i$ проверка имеет вид

$$
f(i, x) = (a[i] \ge x).
$$

> [!NOTE]
> В олимпиадном коде такую функцию чаще называют `check`. Она получает кандидата на ответ и возвращает `true` или `false`.

> [!NOTE]
> В рассуждениях подходящие значения будем отмечать знаком `+`, а неподходящие знаком `-`. В коде этим знакам соответствуют `true` и `false`.

> [!IMPORTANT]
> Чтобы бинарный поиск мог сужать пространство ответов, результаты `check` должны быть **монотонными**.
>
> Для поиска первого подходящего значения это означает: сначала идут только минусы, затем появляется первый плюс, а дальше остаются только плюсы.

Рассмотрим тот же массив и $x=8$:

| индекс $i$ | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `a[i]` | 1 | 3 | 3 | 7 | 10 | 14 | 20 |
| `a[i] >= 8` | - | - | - | - | + | + | + |

Первый плюс стоит на позиции $4$. Он не может оказаться раньше, потому что массив отсортирован: все элементы перед $10$ не превосходят $7$, а все элементы после $10$ не меньше $10$.

Другой монотонный вопрос для того же массива и $x=3$ – `a[i] <= 3`:

| индекс $i$ | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `a[i] <= 3` | + | + | + | - | - | - | - |

> [!IMPORTANT]
> Если подходящие значения находятся слева, храним левую границу как подходящую, правую – как неподходящую и в конце возвращаем `low`.

Здесь полезной границей будет последний плюс, индекс $2$. Это зеркальная версия той же идеи.

Монотонность объясняет каждый шаг поиска:

- Если середина оказалась в зоне минусов, первый плюс не мог быть ни в середине, ни левее неё: левую половину можно отбросить.
- Если середина в зоне плюсов, первый плюс не правее середины: отбрасываем правую половину.

> [!CAUTION]
> Без свойства «один перелом между минусами и плюсами» такое рассуждение не работает.

В следующей главе массив перестанет быть единственным пространством поиска. Мы будем выбирать кандидат на ответ из числового отрезка и строить `check` по условию задачи, но полуинтервал, две роли границ и требование монотонности останутся теми же.

## 6. Бинарный поиск по ответу

Вот мы и добрались до **бинарного поиска по ответу**. В первой главе кандидатами были индексы отсортированного массива. Теперь кандидат – сама величина, которую требует найти задача. Массива с готовыми ответами перед нами нет, но мы умеем спросить для любого кандидата: подходит он или нет?

> [!TIP]
> Прежде чем писать бинарный поиск по ответу, ответьте на три вопроса:
>
> - Что является ответом и в каком диапазоне эта величина лежит?
> - Монотонна ли проверка кандидата?
> - Можно ли быстро проверить, подходит ли фиксированный кандидат?
>
> Если на все три вопроса есть ответ, задачу часто можно решить бинарным поиском.

**Рассмотрим задачу**. Есть $n$ $(1 \le n \le 10^{18})$ единичных квадратов. Разрешается взять некоторые из них и сложить в квадрат со стороной $k$. Требуется найти максимальное целое $k$.

**Решение**. Задача сама подсказывает пространство ответов: искать нужно сторону $k$. Для квадрата $k \times k$ потребуется ровно $k^2$ единичных квадратов.

Проверка кандидата получается короткой:

$$
\text{check}(k) = (k^2 \le n).
$$

> [!IMPORTANT]
> Проверка **монотонна**. Если квадрат со стороной $k$ можно собрать, то квадрат со стороной $k-1$ получится автоматически после удаления одной строки и одного столбца.
>
> Если квадрата со стороной $k$ собрать нельзя, то квадрат со стороной $k+1$ тем более собрать не получится.
>
> Для корректности достаточно доказать одну из этих двух сторон монотонности. Вторая здесь нужна только для полноты картины.

Подходящие значения находятся слева, поэтому ищем последний плюс. В коде `low` будет подходящим значением, а `high` – неподходящим.

<details>
<summary><strong>C++: максимальная сторона квадрата</strong></summary>

```cpp
#include <bits/stdc++.h>
using namespace std;
main() {
    ios::sync_with_stdio(false);
    cin.tie(0);
    // Читаем число доступных единичных квадратов.
    int64_t n; cin >> n;
    // low подходит, high не подходит. При такой high квадрат mid помещается в int64_t.
    int64_t low = 1, high = 2'000'000'000LL;
    while (high - low > 1) {
        int64_t mid = (low + high) / 2;
        if (mid * mid <= n) low = mid;
        else high = mid;
    }
    cout << low << '\n';
}
```

</details>

<details>
<summary><strong>Python3: максимальная сторона квадрата</strong></summary>

```python
# Читаем число доступных единичных квадратов.
n = int(input())
# low подходит, high не подходит.
low, high = 1, 2_000_000_000
while high - low > 1:
    mid = (low + high) // 2
    if mid * mid <= n: low = mid
    else: high = mid
print(low)
```

</details>

Полные программы: [C++](Part-02-Binary-Search-on-Answer/examples/example-01.cpp) и [Python3](Part-02-Binary-Search-on-Answer/examples/example-01.py).

<details>
<summary><strong>Пример запуска</strong></summary>

```text

300

Вывод
17
```

</details>

Проверка работает за $O(1)$, а длина пространства ответов не больше $2 \cdot 10^9$. Поэтому поиск требует $O(\log(10^9))$ времени и $O(1)$ дополнительной памяти.

## 7. Как задать границы и выбрать типы данных?

Если мы подумаем, то из условия задачи следует, что ответ ограничен числом $10^9$. Но это не значит, что верхняя граница полуинтервала обязана равняться $10^9 + 1$ в вашем коде.

> [!IMPORTANT]
> Для поиска последнего подходящего значения верхняя граница не обязана быть минимальной неподходящей.

Здесь `low = 1` подходит, потому что $n$ натурально. Любое число больше $10^9$ не подходит. Например, можно взять `high = 1'111'111'111LL`. В рабочей версии выбрано `2'000'000'000LL`: это простая граница с запасом.

> [!WARNING]
> Граница «с запасом» остаётся допустимой только после доказательства, что она не подходит. Если `high` подходит, бинарный поиск может завершиться с неверным ответом.

> [!TIP]
> Если проверка уже доказана, но при отправке получается `Wrong Answer`, проверьте границы. В частности, можно временно увеличить `high` в два раза и повторно проверить её неподходящесть.
>
> Это быстрый способ проверить гипотезу о слишком маленьком диапазоне, но не замена доказательству.

Ещё один практический совет: **не жадничайте с типами**. В задачах на поиск ответа границы, середина и промежуточные произведения быстро становятся больше обычного `int`.

> [!TIP]
> Для целых границ и вычислений сразу выбирайте `int64_t`, если ограничения допускают большие числа.
>
> - `low + high` не переполнится при наших границах.
> - Середина всегда меньше `high`, поэтому произведение `mid * mid` меньше $4 \cdot 10^{18}$ и также помещается в `int64_t`.
> - При необходимости верхнюю границу можно увеличить, не переписывая весь код под другой тип.

Выражения приведения к 64-битному типу вроде `mid * 1LL * mid` выглядят круто, но не помогают сдать правильное решение без багов раньше конкурентов.

## 8. Почему не `sqrt`?

Математически ответ равен $\lfloor\sqrt{n}\rfloor$. Кажется, что можно вычислить `sqrt(n)`, отбросить дробную часть и закончить задачу без бинарного поиска. Проблема в том, что обычный `sqrt` работает с `double` и может округлить значение вверх.

В GCC есть специальный вариант `sqrtl`, который возвращает `long double`. При данных ограничениях выражение `(int64_t)sqrtl(n)` даёт правильный ответ, но опирается на точность `long double` в конкретном компиляторе.

Пусть $p = 999\,999\,999$. Для $n = p^2 - 1$ верный ответ равен $p - 1 = 999\,999\,998$. Однако на обычных реализациях с числами IEEE 754 следующий код печатает $999\,999\,999$.

<details>
<summary><strong>C++: ненадёжный вариант с sqrt</strong></summary>

```cpp
#include <bits/stdc++.h>
using namespace std;
main() {
    ios::sync_with_stdio(false);
    cin.tie(0);
    // Демонстрация: преобразование результата sqrt может дать неверный целый корень.
    int64_t n; cin >> n;
    cout << (int64_t)sqrt(n) << '\n';
}
```

</details>

<details>
<summary><strong>Python3: ненадёжный вариант с sqrt</strong></summary>

```python
import math
# Демонстрация: преобразование результата sqrt может дать неверный целый корень.
n = int(input())
print(int(math.sqrt(n)))
```

</details>

Полные демонстрационные программы: [C++](Part-02-Binary-Search-on-Answer/examples/example-02.cpp) и [Python3](Part-02-Binary-Search-on-Answer/examples/example-02.py).

> [!CAUTION]
> Преобразование `sqrt(n)` к целому типу не является надёжным способом получить целый квадратный корень.
>
> В GCC при данных ограничениях можно использовать `(int64_t)sqrtl(n)`, но этот приём зависит от точности `long double`.
> 
> Бинарный поиск работает только с целыми числами и не зависит от этой особенности компилятора.

Можно оставить обычный `sqrt`, но считать его результат только начальным кандидатом. Сначала увеличиваем $k$, пока следующий кандидат подходит, затем уменьшаем $k$, пока текущий кандидат не подходит. После этих двух проверок выполнено $k^2 \le n < (k + 1)^2$, поэтому $k = \lfloor\sqrt{n}\rfloor$.

> [!TIP]
> После вычисления приближённого ответа проверяйте его тем же целочисленным предикатом, который определяет правильный ответ.

В C++ этот приём выглядит так:

```cpp
int64_t k = sqrt(n);
while ((k + 1) * (k + 1) <= n) k++;
while (k * k > n) k--;
cout << k << '\n';
```

В Python проверки те же:

```python
k = int(math.sqrt(n))
while (k + 1) * (k + 1) <= n: k += 1
while k * k > n: k -= 1
print(k)
```

При данных ограничениях `sqrt` с `double` промахивается не более чем на единицу, поэтому выполнится не больше одной итерации одного из циклов. Целочисленная проверка всё равно нужна: именно она превращает приближённый результат в точный.

## 9. Последовательность квадратов

**Рассмотрим задачу**. Есть $n$ $(1 \le n \le 10^{18})$ единичных квадратов. Сначала собираем квадрат $1 \times 1$ и кладём его на стол. Затем из оставшихся квадратов собираем квадрат $2 \times 2$ и кладём справа от первого. Продолжаем со сторонами $3$, $4$ и так далее, пока квадратов хватает. Требуется найти число полных квадратов на столе.

**Решение с формулой**. На шаге $i$ расходуется $i^2$ единичных квадратов. Чтобы выложить первые $k$ квадратов, потребуется

$$
S(k) = 1^2 + 2^2 + \dots + k^2 = \frac{k(k + 1)(2k + 1)}{6}.
$$

Например, при $n = 100$ первые шесть квадратов потребуют $1 + 4 + 9 + 16 + 25 + 36 = 91$ клетку, а седьмой увеличит расход до $140$. Ответ равен $6$.

Подходит кандидат $k$, для которого $S(k) \le n$. Предикат монотонен: если на первые $k$ квадратов хватает клеток, то хватит и на первые $k - 1$. Поэтому снова ищем последний плюс.

<details>
<summary><strong>C++: бинарный поиск с формулой суммы квадратов</strong></summary>

```cpp
#include <bits/stdc++.h>
using namespace std;
int64_t sumSquares(int64_t k) {
    return k * (k + 1) * (2 * k + 1) / 6;
}
main() {
    ios::sync_with_stdio(false);
    cin.tie(0);
    // Ищем последнее k, для которого хватает квадратов на все фигуры от 1 до k.
    int64_t n; cin >> n;
    int64_t low = 0, high = 1'500'000;
    while (high - low > 1) {
        int64_t mid = (low + high) / 2;
        if (sumSquares(mid) <= n) low = mid;
        else high = mid;
    }
    cout << low << '\n';
}
```

</details>

<details>
<summary><strong>Python3: бинарный поиск с формулой суммы квадратов</strong></summary>


Проверка занимает $O(1)$, поиск – $O(\log(\sqrt[3]{n}))$, а дополнительная память – $O(1)$.

**Решение без формулы**. Можно не помнить сумму квадратов. Заведём `sums`, где `sums[k]` – расход на первые $k$ квадратов. Начинаем с `sums[0] = 0` и добавляем $k^2$, пока следующее значение не превысит $10^{18}$. Массив строго возрастает, поэтому `upper_bound` в C++ и `bisect_right` в Python найдут первое значение больше $n$. Его предыдущий индекс и будет ответом.

> [!TIP]
> Префиксные суммы строятся один раз. Если в задаче много запросов с разными $n$, одну и ту же таблицу можно использовать для всех них.

<details>
<summary><strong>C++: префиксные суммы без формулы</strong></summary>

```cpp
#include <bits/stdc++.h>
using namespace std;
main() {
    ios::sync_with_stdio(false);
    cin.tie(0);
    // Храним все возможные расходы, не превосходящие ограничение на n.
    vector<int64_t> sums = {0};
    for (int64_t k = 1; sums.back() + k * k <= 1'000'000'000'000'000'000LL; k++)
        sums.push_back(sums.back() + k * k);
    // Отвечаем на запрос последним расходом, не превосходящим n.
    int64_t n; cin >> n;
    cout << upper_bound(sums.begin(), sums.end(), n) - sums.begin() - 1 << '\n';
}
```

</details>

<details>
<summary><strong>Python3: префиксные суммы без формулы</strong></summary>

Полные программы: [C++](Part-02-Binary-Search-on-Answer/examples/example-04.cpp) и [Python3](Part-02-Binary-Search-on-Answer/examples/example-04.py).

Предподсчёт создаёт $1\,442\,249$ положительных значений и занимает $O(k)$ времени и памяти. После него один запрос обрабатывается за $O(\log(k))$. Для одного $n$ вариант с формулой легче и быстрее, а для многих запросов предподсчёт остаётся удобной альтернативой.

**Почему не кубическое уравнение**. Если подставить формулу в равенство $S(k) = n$, получится

$$
2k^3 + 3k^2 + k - 6n = 0.
$$

Все три корня можно записать непосредственно через $n$:

$$
\begin{aligned}
k_1 &= \frac{\sqrt[3]{12n + \sqrt{144n^2 - \frac{1}{27}}} + \sqrt[3]{12n - \sqrt{144n^2 - \frac{1}{27}}} - 1}{2}, \\
k_2 &= \frac{\frac{-1 + i\sqrt{3}}{2}\sqrt[3]{12n + \sqrt{144n^2 - \frac{1}{27}}} + \frac{-1 - i\sqrt{3}}{2}\sqrt[3]{12n - \sqrt{144n^2 - \frac{1}{27}}} - 1}{2}, \\
k_3 &= \frac{\frac{-1 - i\sqrt{3}}{2}\sqrt[3]{12n + \sqrt{144n^2 - \frac{1}{27}}} + \frac{-1 + i\sqrt{3}}{2}\sqrt[3]{12n - \sqrt{144n^2 - \frac{1}{27}}} - 1}{2}.
\end{aligned}
$$

> [!NOTE]
> При $n \ge 1$ первый корень вещественный, а второй и третий образуют комплексно-сопряжённую пару. Математический ответ задачи равен целой части первого корня.

<details>
<summary><strong>Вывод через формулы Кардано</strong></summary>

Сделаем замену $t = 2k + 1$. Тогда

$\frac{t^3 - t}{4} = 6n, \qquad t^3 - t - 24n = 0$.

Это пониженное кубическое уравнение. Обозначим

$D = 144n^2 - \frac{1}{27}, \qquad u = \sqrt[3]{12n + \sqrt{D}}, \qquad v = \sqrt[3]{12n - \sqrt{D}}$.

Пусть $\omega = \frac{-1 + i\sqrt{3}}{2}$, где $\omega^3 = 1$ и $\omega \ne 1$. По формуле Кардано получаем

$k_1 = \frac{u + v - 1}{2}$.

$k_2 = \frac{\omega u + \omega^2 v - 1}{2}$.

$k_3 = \frac{\omega^2 u + \omega v - 1}{2}$.

</details>

Формула даёт точное выражение, но для программы его всё равно нужно привести к целому и исправить циклами с проверкой $S(k) \le n$. Такая реализация длиннее бинарного поиска, зависит от вычислений с вещественными числами и требует целочисленной проверки в конце.

> [!WARNING]
> Простой `cbrt(n)` задаёт лишь порядок ответа, а не близкое значение самого $k$. При $n = 10^{18}$ оно равно $10^6$, тогда как правильный ответ равен $1\,442\,249$. Цикл, который увеличивает такой кандидат на единицу, выполнит более $400\,000$ шагов. На версии задачи с несколькими тестами это не заменяет бинарный поиск.

В следующей главе мы сохраним тот же подход, но проверка перестанет быть одной формулой. Сам цикл бинарного поиска останется коротким, а главной частью решения станет `check`.

## 10. Проверка кандидата в отдельной функции

В прошлой главе проверка кандидата была короткой формулой. Но в задачах поинтереснее для фиксированного ответа нужно сначала построить план: выбрать элементы, сопоставить пары, посчитать цену этого плана. Если писать всё внутри цикла бинарного поиска, сам поиск теряется среди деталей задачи.

Поэтому <u>вынесем проверку кандидата в функцию `check`</u>. Она получает только кандидат `x` и отвечает на один вопрос: может ли `x` быть ответом. Все остальные данные уже прочитаны и при необходимости подготовлены до бинарного поиска.

```cpp
bool check(int64_t x) {
    // Проверяем, может ли x быть ответом на задачу?
    ...
}
while (high - low > 1) {
    int64_t mid = (low + high) / 2;
    if (check(mid)) low = mid;
    else high = mid;
}
cout << low << endl;
```

Здесь, как и раньше, `low` подходит, а `high` не подходит. Цикл ничего не знает о смысле кандидата. Он лишь находит последний плюс в монотонной последовательности значений `check`.

> [!IMPORTANT]
> У `check(x)` должен быть точный смысл. Для задачи на максимум она обычно отвечает «можно получить **хотя бы** `x`». Тогда из `check(x) = true` автоматически следует `check(x - 1) = true`, и бинарный поиск ищет последнюю подходящую границу.

Разделение полезно по трём причинам. Во-первых, внешний цикл больше не меняется от задачи к задаче. Во-вторых, доказательство корректности распадается на две независимые части: мы доказываем точность `check` и её монотонность. В-третьих, проверку легко отладить отдельно: подставить конкретный `x`, вручную построить план и сравнить его цену с тем, что посчитала функция.

> [!TIP]
> Сначала напишите и проверьте `check` для нескольких значений кандидата, а уже затем оборачивайте её бинарным поиском. Если функция ошибается для фиксированного `x`, смена границ `low` и `high` этого не исправит.

В следующих двух задачах цикл будет одинаковым. Изменится только содержимое `check`: сначала она выберет выгодные элементы одного массива, затем составит выгодные пары в игре.

## 11. Сколько чисел можно поднять до порога?

**Рассмотрим задачу**. Даны $n$ $(1 \le n \le 2 \cdot 10^5)$ чисел $a_i$ $(0 \le a_i \le 10^9)$, запас $k$ $(0 \le k \le 10^{18})$ единичных увеличений и порог $x$ $(1 \le x \le 10^9)$. За одно увеличение разрешается прибавить $1$ к любому числу. Требуется найти наибольшее количество чисел, которые можно сделать больше либо равными $x$.

**Решение**. Пусть кандидат `mid` означает, что мы хотим подготовить хотя бы `mid` чисел. Тогда `check(mid)` должна вернуть `true` тогда и только тогда, когда минимальная цена такой подготовки не превосходит $k$.

**Предикат монотонен**. Если удалось поднять `mid` чисел, можно оставить только `mid - 1` из них и получить меньший результат. Поэтому последовательность проверок имеет вид `+ + ... + - - ... -`, а бинарный поиск действительно найдёт максимум.

Остаётся найти **минимальную цену**, с помощью которой мы достигнем ответ `>= mid`. Сначала отсортируем массив. Для подготовки выгодно выбрать `mid` наибольших чисел и увеличивать только их.

<details>
<summary><strong>Почему выбираем самые большие числа?</strong></summary>

Пусть выбрано число $a_p$, а большее $a_q$ осталось вне выбора. Если заменить $a_p$ на $a_q$, нужное число увеличений не вырастет: $\max(0, x - a_q) \le \max(0, x - a_p)$.

Повторяя такой обмен, получаем первые `mid` чисел массива, отсортированного по убыванию.

</details>

Для каждого из них нужно доплатить недостачу до $x$, если она есть. Минимальная цена равна

$$
C(\text{mid}) = \sum_{i=0}^{\text{mid}-1} \max(0, x - a_i).
$$

Значит, `check(mid)` вычисляет эту сумму и сравнивает её с $k$. Как только накопленная цена стала больше $k$, функция сразу возвращает `false`: точное значение суммы уже не влияет на ответ.

Разберём массив $a = [1, 2, 8, 9]$, порог $x = 10$ и запас $k = 3$.

| `mid` | выбранные числа | минимальная цена | `check(mid)` |
| ---: | --- | ---: | --- |
| 0 | нет | 0 | + |
| 1 | 9 | 1 | + |
| 2 | 8, 9 | 3 | + |
| 3 | 2, 8, 9 | 11 | - |
| 4 | 1, 2, 8, 9 | 20 | - |

Последний плюс находится при `mid = 2`, это и есть ответ.

> [!IMPORTANT]
> В `check` не нужно искать какой-нибудь допустимый набор элементов. Нужен набор с **минимальной** ценой. Только после этого сравнение с $k$ честно отвечает на вопрос, достижим ли кандидат.

Полная программа повторяет общий шаблон. Сортировка по убыванию выполняется один раз до поиска, а `check` проходит по выбранному префиксу массива.

<details>
<summary><strong>C++: сколько чисел можно поднять до x</strong></summary>

```cpp
#include <bits/stdc++.h>
using namespace std;
bool check(const auto& a, int64_t x, int64_t k, int mid) {
    // Считаем цену подготовки mid наибольших чисел.
    int64_t need = 0;
    for (int i = 0; i < mid; i++) {
        need += max(0LL, x - a[i]);
        if (need > k) return false;
    }
    return true;
}
main() {
    ios::sync_with_stdio(false);
    cin.tie(0);
    // Читаем числа, запас увеличений и порог.
    int n; int64_t k, x;
    cin >> n >> k >> x;
    vector<int64_t> a(n);
    for (auto& it : a) cin >> it;
    // Сортируем по убыванию, чтобы улучшать первые элементы.
    sort(a.rbegin(), a.rend());
    // Ищем наибольшее достижимое количество подготовленных чисел.
    int low = 0, high = n + 1;
    while (high - low > 1) {
        int mid = (low + high) / 2;
        if (check(a, x, k, mid)) low = mid;
        else high = mid;
    }
    // Выводим максимальное количество.
    cout << low << '\n';
}
```

</details>

<details>

## 12. Игра с двумя мультимножествами

Теперь усложним проверку. Есть два игрока и два мультимножества чисел. До игры мы можем увеличить свои числа, а затем начать играть. Каждый раунд состоит из шагов:
1. Соперник выбирает число из своего мультимножества и кладёт его на стол;
2. Мы выбираем число из нашего мультимножества и кладём его на стол.

Если наше число больше либо равно числу соперника, мы получаем очко. Требуется максимизировать число очков.

Это излюбленный баян соревнований по спортивному программированию (Яндекс Алгоритм, РуКод, ICPC, т.д.). Внешне задача похожа на игру, но после того как известны оба мультимножества, надо не моделировать ходы, а составить выгодные пары.

**Формально** даны $n$ $(1 \le n \le 2 \cdot 10^5)$ чисел $a_i$ $(0 \le a_i \le 10^9)$, $n$ чисел $b_i$ $(0 \le b_i \le 10^9)$ и запас $k$ $(0 \le k \le 10^{18})$ единичных увеличений для чисел первого игрока. Соперник выкладывает число из $b$, затем первый игрок отвечает числом из $a$. До начала игры разрешается потратить не более $k$ увеличений на числа из $a$. Найдите наибольшее число очков первого игрока.

**Решение**. Фиксируем `mid`: хотим получить хотя бы `mid` побед.

Проверим **монотонность**. Если есть план на `mid` очков, достаточно оставить в нём любые `mid - 1` запланированных побед. При этом на остальных парах иногда тоже получится победить без вложений, но лишнее очко не мешает предикату «хотя бы `mid`».

Сортируем оба мультимножества.

> [!IMPORTANT]
> После сортировки по возрастанию берём суффикс `a[n - mid] ... a[n - 1]` из `mid` максимальных наших чисел и префикс `b[0] ... b[mid - 1]` из `mid` минимальных чисел соперника.
>
> Сопоставляем их последовательно: `a[n - mid]` ставим против `b[0]`, затем `a[n - mid + 1]` против `b[1]` и так далее.
>
> Остальные числа можно сопоставить как угодно, не беспокоясь о результате: они не важны для плана получить хотя бы `mid` очков.

<details>
<summary><strong>Почему этот план имеет минимальную цену?</strong></summary>

Выбор первых обосновывается тем же обменом, что и в предыдущей задаче: большее своё число не дороже поднять до любой цели. Выбор вторых тоже обосновывается обменом: если мы готовы победить большее число соперника, то тем же своим числом победим меньшее не дороже.

Почему сопоставляем именно в этом порядке? Пусть два своих числа $p \le q$, а два числа соперника $r \le s$. В последовательном варианте получаются пары $p$ с $r$ и $q$ с $s$. Если они перекрещены, то есть $p$ поставлено против $s$, а $q$ против $r$, поменяем числа соперника местами. Большая цель $s$ достаётся не меньшему числу $q$, поэтому суммарная недостача не растёт. Повторяя такой обмен, приходим к последовательному сопоставлению суффикса `a` и префикса `b`.

</details>

Таким образом, минимальная цена `mid` запланированных побед равна

$$
C(\text{mid}) = \sum_{i=0}^{\text{mid}-1} \max(0, b_i - a_{n-\text{mid}+i}).
$$

Здесь слагаемое с `i = 0` – цена пары `b[0]` и `a[n - mid]`, а слагаемое с `i = mid - 1` – цена пары `b[mid - 1]` и `a[n - 1]`. Именно эту сумму считает `check(mid)`: она последовательно бьёт префикс `b` суффиксом `a`. В ней появились два решения, которых не было в первой задаче: какие числа выбрать с обеих сторон и как составить пары. А цикл бинарного поиска остался прежним.

Разберём $a = [1, 2, 8, 9]$, $b = [3, 7, 10, 12]$ и $k = 3$. Для `mid = 3` план выглядит так:

| роль пары | число соперника | наше число | цена увеличений |
| --- | ---: | ---: | ---: |
| не планируем очко | 12 | 1 | 0 |
| планируем очко | 3 | 2 | 1 |
| планируем очко | 7 | 8 | 0 |
| планируем очко | 10 | 9 | 1 |

Цена равна $2$, поэтому `check(3)` возвращает `true`. Для `mid = 4` придётся поднять все свои числа. Цена станет $2 + 5 + 2 + 3 = 12$, она больше $k$. Ответ равен $3$.

> [!WARNING]
> Стоимость пары равна `max(0, b[i] - a[j])`, а не просто `b[i] - a[j]`. Уже выигранная пара не возвращает увеличения в запас, её цена равна нулю.

<details>
<summary><strong>C++: максимальное число побед</strong></summary>

```cpp
#include <bits/stdc++.h>
using namespace std;
bool check(const auto& a, const auto& b, int64_t k, int mid) {
    // Считаем цену mid запланированных побед.
    int64_t need = 0;
    int firstWin = a.size() - mid;
    for (int i = 0; i < mid; i++) {
        need += max(0LL, b[i] - a[firstWin + i]);
        if (need > k) return false;
    }
    return true;
}
main() {
    ios::sync_with_stdio(false);
    cin.tie(0);
    // Читаем оба мультимножества и запас увеличений.
    int n; int64_t k; cin >> n >> k;
    vector<int64_t> a(n), b(n);
    for (auto& it : a) cin >> it;
    for (auto& it : b) cin >> it;
    // Сортируем, чтобы сопоставлять малые и большие значения по ролям.
    sort(a.begin(), a.end());
    sort(b.begin(), b.end());
    // Ищем наибольшее достижимое количество побед.
    int low = 0, high = n + 1;
    while (high - low > 1) {
        int mid = (low + high) / 2;
        if (check(a, b, k, mid)) low = mid;
        else high = mid;
    }
    // Выводим максимальное количество побед.
    cout << low << '\n';
}
```

</details>

## 13. Вещественный бинарный поиск по ответу

В предыдущих главах кандидат был целым числом. Как только между `low` и `high` не оставалось целого значения, поиск завершался. Для вещественных чисел соседних значений нет: между $2$ и $2{,}000001$ лежит бесконечно много кандидатов.

Значит, в задачах с вещественным ответом мы не находим число в точности. Мы поддерживаем отрезок, в котором лежит ответ, и сужаем его до заранее выбранной точности. Сама идея из прошлой главы не меняется: `check(x)` отвечает, подходит ли кандидат $x$, а бинарный поиск сохраняет подходящую левую и неподходящую правую границы.

```cpp
using ld = long double;
ld low = ..., high = ...;
for (int iter = 0; iter < 100; iter++) {
    ld mid = (low + high) / 2;
    if (check(mid)) low = mid;
    else high = mid;
}
cout << fixed << setprecision(10) << low << '\n';
```

> [!IMPORTANT]
> После каждой итерации `low` остаётся подходящим, а `high` – неподходящим. Поэтому печатаем `low`: это гарантированно допустимое приближение ответа снизу.

За один шаг расстояние между границами уменьшается вдвое. Если исходная ширина отрезка равна $r$, то после $t$ шагов она равна

$$
\frac{r}{2^t}.
$$

Чтобы получить абсолютную погрешность не больше $\varepsilon$, достаточно выбрать

$$
t \ge \left\lceil \log_2\left(\frac{r}{\varepsilon}\right) \right\rceil.
$$

На практике часто выполняют $100$ итераций. При начальной ширине не больше $10^9 + 1$ математическая ширина интервала после них меньше $10^{-20}$. Это намного точнее обычного требования $10^{-6}$, а фиксированное число шагов избавляет от ненадёжного сравнения вещественных чисел в условии остановки.

> [!TIP]
> Сначала оцените начальную ширину отрезка и требуемую точность, затем выберите число итераций с запасом. Не ждите, что `mid` когда-либо совпадёт с точным ответом.

Посмотрим, как такой поиск работает в задаче.

## 14. Нарезка отрезков

**Рассмотрим задачу**. Даны $n$ $(1 \le n \le 2 \cdot 10^5)$ отрезков целой длины $a_i$ $(1 \le a_i \le 10^9)$ и число $m$ $(1 \le m \le 10^9)$. Каждый отрезок разрешается разрезать на части одной и той же одинаковой вещественной длины $x$, остатки выбрасываются. Требуется найти наибольшую длину $x$, из которой получится не меньше $m$ частей.

**Решение.** Пусть `check(x)` проверяет длину одной части $x$. Из отрезка длины $a_i$ можно получить $\left\lfloor a_i / x \right\rfloor$ полных частей. Значит, суммарное число частей равно

$$
P(x) = \sum_{i=1}^{n} \left\lfloor \frac{a_i}{x} \right\rfloor.
$$

Кандидат подходит, если $P(x) \ge m$.

Проверка на **монотонность**. При увеличении $x$ каждое слагаемое в этой сумме не возрастает. Поэтому если длина $x$ подходит, то любая меньшая положительная длина тоже подходит. Подходящие значения стоят слева, неподходящие справа, и снова можно искать границу между `+` и `-`.

Разберём отрезки $[5, 8, 3]$ и $m = 7$.

| длина части $x$ | части из 5 | части из 8 | части из 3 | всего | `check(x)` |
| ---: | ---: | ---: | ---: | ---: | --- |
| 3 | 1 | 2 | 1 | 4 | - |
| 2,5 | 2 | 3 | 1 | 6 | - |
| 2 | 2 | 4 | 1 | 7 | + |
| 1,5 | 3 | 5 | 2 | 10 | + |

Граница находится в точке $2$. В отличие от целого поиска, алгоритм не должен увидеть именно это число. Достаточно сделать интервал между границами существенно меньше разрешённой ошибки.

> [!NOTE]
> В этой задаче требуется **хотя бы** $m$ частей, а не ровно $m$. При меньшей длине частей может получиться больше, и это только подтверждает, что кандидат подходит.

## 15. Границы, проверка и точность

Для левой границы берём `low = 0`. Это служебная подходящая граница, но `check(0)` вызывать нельзя: в ней было бы деление на ноль. В первом и всех следующих шагах `mid` строго больше нуля, поэтому проверка получает только допустимые длины.

Правая граница `high = max(a) + 1` точно не подходит. Самый длинный исходный отрезок короче `high`, поэтому не даст даже одной части такой длины. Итак, перед началом поиска ответ лежит между `low` и `high`.

В `check` последовательно суммируем число частей. Полная сумма может быть гораздо больше $m$, но большего нам знать не нужно. Как только частей стало хотя бы $m$, возвращаем `true`. В C++ это заодно защищает счётчик от переполнения: если число частей от очередного отрезка уже достаточно, функция завершится до преобразования его к `int64_t`.

> [!WARNING]
> Не заменяйте досрочную проверку строкой `pieces += length / x`. Для очень маленького $x$ значение может не поместиться в целочисленный счётчик, хотя ответ `true` уже известен.

После $100$ делений пополам печатаем `low` с десятью знаками после запятой. В C++ для вычислений выбран `long double` с обычным олимпиадным сокращением `ld`, в Python обычный `float` уже даёт достаточную точность для этой задачи.

<details>
<summary><strong>C++: нарезка отрезков</strong></summary>

```cpp
#include <bits/stdc++.h>
using namespace std;
using ld = long double;
bool check(const auto& a, int64_t m, ld x) {
    int64_t pieces = 0;
    for (auto it : a) {
        ld count = it / x;
        if (count >= m - pieces) return true;
        pieces += (int64_t)count;
    }
    return false;
}
main() {
    ios::sync_with_stdio(false);
    cin.tie(0);
    // Ищем наибольшую длину, из которой получится хотя бы m отрезков.
    int n; int64_t m; cin >> n >> m;
    vector<int64_t> a(n);
    for (auto& it : a) cin >> it;
    ld low = 0, high = *max_element(a.begin(), a.end()) + 1;
    for (int iter = 0; iter < 100; iter++) {
        ld mid = (low + high) / 2;
        if (check(a, m, mid)) low = mid;
        else high = mid;
    }
    cout << fixed << setprecision(10) << low << '\n';
}
```

</details>
